## 1. What the system is

A **multi-tenant creative-performance analytics tool** for paid social. It manages 2–5 brands from one database, ingests platform exports (CSV/XLSX) through a strict validation pipeline, and serves read-heavy dashboards that answer "which creatives and campaigns are working, where, and why".

- **Platforms:** `instagram`, `facebook`, `tiktok`, `snapchat` (Meta is split into IG + FB; a short ` (IG)`/` (FB)` tag keeps the same Meta campaign distinct per channel).
- **Data enters ONLY via upload** (no ad-platform API sync, no background jobs, no queues — a deliberate scope decision; see `docs/system-strategy-review.md`).
- **Production:** https://creative.urjwan.com — live, in daily use.

## 3. Architecture

- **Server Components by default.** `"use client"` only for interactivity. Pages compose one view; **all data fetching lives in `db/queries/*`** (account-scoped), never inline in pages.
- **Mutations are Server Actions** (`app/actions/*` — 24 files). There is **no REST API surface** except: `POST /api/uploads/validate`, `POST /api/uploads/commit`, `POST /api/uploads/thumbnail` (file uploads need routes), `GET /api/health` (public health check: 200 ok / 503 degraded), and the **MCP server** at `/api/mcp/mcp` (bearer-authed, read-only — see §MCP server).
- **Auth boundary:** `middleware.ts` verifies the session cookie signature/TTL at the Edge for every route except `/signin`, `/api/health`, **`/api/mcp`** (its own bearer auth), `_next`, and root-level static assets. The dashboard layout re-checks and role/permission gates apply per action (defense in depth). A drift-pin test asserts the middleware's Web Crypto verifier accepts tokens signed by `lib/auth-cookie.ts`.
- **Single sources of truth in `lib/`** — never open-code these elsewhere:
  - `lib/metrics.ts` — every derived-metric SQL fragment (see §7)
  - `lib/palette.ts` — platform/series/product/type/funnel-metric colors (CSS-var backed, theme-aware) + platform labels/lists
  - `lib/format.ts` — usd/int/pct/`roas()`/compact/`monthDay`/isoDate (en-US pinned)
  - `lib/metric-labels.ts` — column-header vocabulary (one spelling of "Impr."/"Conv.")
  - `lib/permissions.ts` — the permission catalog (see §5)
  - `lib/campaign.ts` `buildCampaignName()` — the only builder of campaign registry names
  - `csv/platforms/types.ts` — `INTERNAL_FIELDS`/`FIELD_META`, typed so a new field fails compilation anywhere it isn't described
- **Navigation feedback:** any component driving route/searchParam changes uses `useNavTransition()` (`lib/nav-progress.ts`) so the global progress bar reflects pending navigation.

## 4. Data model (27 tables)

**Tenancy & people:** `accounts` (brands; `status_window_hours` per brand; `usd_to_sar_rate` numeric default 3.77 — the Budget module's per-brand display/ROAS rate), `users` (role tier + granular `permissions` + `all_accounts` brand-membership flag, §5), `user_accounts` (brand membership — the brands a restricted `all_accounts = false` user may see; global join table, both FKs `ON DELETE CASCADE`; consulted only when `all_accounts = false`, §5).
**Catalog:** `products`, `creatives` (required `product_id`; unique per account; the legacy manual `status` column is dead — status is derived, §4.2; `priority smallint` NULLABLE = the team's MANUAL 1–3 importance judgment, 3 = highest, NULL = unrated — detail-page only, distinct from the computed "Rate"/rating concept), `angles`, `creative_angles` (no `account_id` — scoped transitively via the creative; cascading angle operations MUST be bounded by an account-scoped creatives subquery), `creative_platform_overrides` (manual per-creative×platform termination).
**Campaigns:** `campaigns` — the registry. `performance_records.campaign_id` is a NOT NULL FK to it; the display name is the built `Campaign ➤ Adset (IG|FB)` string, created only via `buildCampaignName()`.
**Performance:** `performance_records` — the fact table. **Unique on `(creative_id, platform, campaign_id, date)`.** Carries `excluded_from_aggregates` with provenance (`excluded_source` 'manual'|'rule' + `excluded_rule_id`, 2026-09) and a NOT NULL `upload_batch_id`.
**Exclusion rules:** `exclusion_rules` (2026-09) — account-global rules (kind = campaign objective | campaign | creative, exactly one target column set; `active` switch; per-kind partial unique indexes) that MATERIALIZE into the `performance_records` flag via the engine (`lib/exclusion-rules.ts` + `db/queries/exclusion-rules.ts`) — aggregate queries never change. `users.include_excluded` (nullable) stores each user's remembered Excluded-toggle default.
**Ingestion:** `upload_batches`, `upload_validation_sessions` (validate→commit state, 10-min TTL, account pinned at validate time), `platform_field_mappings` (admin-editable CSV header candidates).
**Budget (§Budget module):** `budget_allocations` (monthly spend plan per platform × objective, USD; `month` = first-of-month; unique `(account_id, month, platform, objective)`), `budget_targets` (one row per month: `planned_revenue_sar` + `reserve_spend_usd` (contingency, default 0 — a stored revenue of 0 reads back as "no target" so reserve-only rows work); unique `(account_id, month)`), `budget_day_weights` (day-weight plan curve: only OVERRIDDEN days stored — `day` 1..31 + `weight` numeric(6,2), absent day = weight 1; unique `(account_id, month, day)`). All tenant tables.
**Config & audit:** `rating_rules` (PK = account_id), `platform_rating_rules` (PK = account_id+platform), `summary_views` (saved views, per-user defaults), `audit_events` (append-only, account-stamped).
**Store (Salla orders — §Store module):** `store_orders` (grain = one order; core cols `order_id`/`order_date`/`total_amount` SAR + `attributes` jsonb for custom fields; unique `(account_id, order_id)`), `store_order_fields` (config: 3 locked core rows + custom fields, accepted `headers[]` for explicit mapping), `store_upload_batches` (per-upload; drives rollback). All tenant tables; separate from the ads `upload_batches`/`performance_records`.

### 4.1 Write/delete invariants

- Nothing writes to `performance_records` except the transactional commit route under a parent batch. **The `excluded_from_aggregates` flag has exactly TWO sanctioned writers:** the manual per-record action (stamps `excluded_source='manual'`) and the exclusion-rules engine (stamps `'rule'` + `excluded_rule_id`; skips already-excluded rows, so the two never overwrite each other; un-applying a rule touches only its own rows; manual un-exclude refuses rule-excluded rows and points at the rule). New/upserted records are stamped against ACTIVE rules inside the commit transaction; deleting a campaign/creative deletes rules targeting it (inside the same transaction). **Four sanctioned delete paths only:** batch rollback (≤24 h, requires `upload.rollback`), the record-cleanup tool (filtered hard-delete, preview-then-confirm), `deleteCreative`, and `deleteCampaign` — each transactional (the FKs have no `ON DELETE CASCADE`; code compensates), permission-gated, confirm-with-summary, audit-logged.
- Every tenant table carries `account_id`; every query in `db/queries/*` injects `eq(accountId, getActiveAccountId())`; every write stamps it. FK targets are re-validated against the active account before writes (the FKs alone only prove global existence).
- Schema changes go through Drizzle migrations — additive whenever possible; **migrations run manually** against the direct Neon URL (§9), never on deploy.

### 4.2 Derived status (not stored)

- **Creative status** (4-state: New / Active / Pause / Terminated) — derived from spend recency per platform, anchored to each platform's own latest `spend > 0` day within the brand's `status_window_hours`; manual termination is sticky per creative×platform. Logic: `lib/creative-status.ts` + `db/queries/creative-status.ts`.
- **Campaign status** (2-state: Active / Inactive) — same anchoring, no override. Logic: `lib/campaign-status.ts` + `db/queries/campaign-status.ts`.
- Because these are derived, status "filters" are applied in the query layer after computation — they can never be a SQL `WHERE`.

- **Rollback warns about since-updated rows (2026-09).** `performance_records.updated_at` (nullable, migration 0038) is written ONLY by the ads upsert UPDATE path; NULL means "never overwritten since import". Both rollback confirms (ads + store) count the batch's rows revised AFTER the batch's own `uploaded_at` and warn prominently — rolling back deletes those rows outright, discarding a later upload's values with them. It is warn-with-confirm, never a block. The comparison runs INSIDE SQL against the batch's stored timestamp: reading it into JS truncates Postgres microseconds and reports a phantom revision on every freshly imported row. The ads rollback audits the count actually deleted (via `.returning()`), not `batch.rows_imported` — the two diverge after a cleanup/entity delete.

## 5. Auth & access control

- **Session cookie:** `<userId>.<issuedAtMs>.<hmac>`, HMAC-SHA256 over `AUTH_SECRET`, `timingSafeEqual`, 30-day server-enforced TTL, future-issued rejection. Changing the format logs every user out — treat as a breaking change.
- **Tiers:** `admin` bypasses all permission checks. Below admin, access is **granular per-user permissions** from the catalog in `lib/permissions.ts` (22 permissions in 6 groups). `users.permissions` NULL ⇒ fall back to the role preset (`editor` preset = legacy editor powers; `viewer` = read-only). Enforcement is server-side via `requirePermission()` in every action/route; the UI additionally hides what the user can't do. **Two extra gates on the auth boundary (2026-09):** the ads commit route (`/api/uploads/validate`→`/commit`) RE-CHECKS brand membership against the caller before writing — the validation-session id is a bearer secret that pins an account, so without this a caller holding someone else's token could write into a brand they don't belong to (403 otherwise; the store commit resolves via `getActiveAccountId` and needs no equivalent). And sign-in is THROTTLED: 5 failed attempts for an email within 15 minutes and the 6th is refused before any password verification, counted from the already-audited `auth.signin_failed` rows (no new table; the window slides, so a success needs no reset). The refusal returns the same generic message and skips hashing, so it is not a timing oracle; throttled attempts audit as `auth.signin_throttled`.
- **Brand membership (WHERE, vs. permissions' WHAT):** `users.all_accounts` (default `true` = every brand, **including brands created later**) + the `user_accounts` join table gate which brands a user may see. **Admins are always effectively all-accounts.** Enforced at tenant resolution (`lib/tenant.ts` + pure `lib/account-access.ts`): `listAccounts()` returns only allowed brands (switcher, Brands tab, `setActiveAccount` all follow); `getActiveAccountId()` honors the `ccms_account` cookie only when it names an allowed brand, else falls back to the user's first allowed brand (a forged/stale cookie is not an error); zero allowed brands → the full-page "No brand access" screen (rendered by the dashboard layout before any tenant query). `listAllAccounts()` is the unfiltered list (Team admin + slug/grant checks).
- **Management UI:** the unified **Team** page (`/admin/users`; `/admin/access` redirects there) — per-user preset selector (Admin/Editor/Viewer/Custom) + grouped permission checkboxes derived from the catalog, plus a **Brands** section (All-brands toggle or per-brand checkboxes; admins forced all-brands). Guardrails: no self-editing (access *and* brands), last admin protected, changes audit-logged (`user.permissions_update`, `user.brands_update`).
- Reading dashboards requires only a valid session and membership in ≥1 brand. Brand switching (`ccms_account` cookie) is scoped to the user's allowed brands — **brand membership IS a security boundary; permissions gate capabilities within a brand.**

## 5b. MCP server (connect your own LLM)

- **What:** a remote MCP server (Streamable HTTP, via `mcp-handler`) at **`/api/mcp/mcp`** so each user can connect their own LLM (Claude Desktop/Code, Cursor, ChatGPT dev-mode, SDKs) to READ-ONLY analytics. Route: `app/api/mcp/[transport]/route.ts` (Node runtime, `maxDuration` 60); tools in `lib/mcp/tools.ts`.
- **Auth = personal access tokens**, NOT the session cookie. `api_tokens` stores only a SHA-256 (`token_hash`, unique) + display `prefix`; the raw `cwz_…` secret is shown ONCE. `lib/api-token.ts` mints/verifies (constant-time compare, rejects revoked, throttled `last_used_at`). A token ACTS AS its owner — brand membership + read scope apply exactly as in the web app. Managed self-serve at `/account/api` (every user owns their tokens; audited `token.create`/`token.revoke`). `/api/mcp` is excluded from the middleware cookie gate — the route's `verifyApiToken` is the boundary.
- **Tenant without cookies:** MCP requests carry no cookie, so `lib/tenant.ts` `runWithTenant(accountId, userId, fn)` sets an `AsyncLocalStorage` override (`lib/tenant-context.ts`) that `getActiveAccountId()`/`auth()` consult FIRST; it validates `accountId` is one of the user's allowed brands before entering — so every `db/queries/*` is tenant-correct with zero changes inside it. Each tool resolves a `brand` arg (name/id) against allowed brands, then runs inside `runWithTenant`.
- **Tools (10, all read-only, Zod-schema'd, compact JSON with a `{brand, range}` echo, reuse `db/queries/*`):** `list_brands`, `get_kpis`, `list_creatives`, `get_creative`, `list_campaigns`, `get_campaign`, `get_summary`, `get_timeseries`, `get_funnel`, `get_data_freshness`. Descriptions state units (USD), date format (YYYY-MM-DD), and that blended metrics are weighted. Guardrails: 60 calls/min per token, ≤500 rows per list tool (`truncated` flag).
- **Scope guard:** v1 is STRICTLY read-only — no tool mutates. OAuth 2.1 for claude.ai-web/ChatGPT-web connectors is out of scope (Phase 2); v1 targets header-auth clients. Migration **0029** (additive: `api_tokens`).

## 5c. Store module (manual Salla order uploads)

- **What:** a top-level **Store** section (in the sidebar's Store group) split into TWO pages — `/store/uploads` (upload history + `/new` flow) and `/store/orders` (the orders table, SAR). `/store` redirect-stubs to `/store/orders`. A NEW module, PARALLEL to and independent of the ads pipeline (touches no `csv/`, `upload_batches`, or `performance_records`).
- **Grain + fields:** one row per order. Exactly THREE core fields — `order_id`/`order_date`/`total_amount` (SAR). Everything else is an admin-defined CUSTOM field (`store_order_fields`: label, type text|number|date, required?, accepted `headers[]`) whose values live in `store_orders.attributes` jsonb. Core rows are seeded per account (migration 0030 + `createAccount`) and LOCKED by `CORE_KEYS` (`store/fields.ts`): only their label + headers are editable. Config UI = the **Order fields** tab on `/store/uploads` (`config.store`; moved there from Configuration in the 2026-09 IA pass). **Every defined field is offered in the Orders table's Columns menu** — visibility is each viewer's per-browser choice (persisted as a HIDDEN-key set, so newly-added fields default to visible). The old per-field `show_in_table` toggle was retired 2026-08 (column kept dead, additive-only).
- **Upload pages (mirrors the ads `/uploads` + `/uploads/new` pattern):** `/store/uploads` is the upload HISTORY (recent batches: filename, when, by, counts, upsert flag, rollback while eligible) with a "New upload" button → `/store/uploads/new`, which hosts the full flow (dropzone → validate → error report/summary → confirm) via `StoreUploadPanel`; a successful commit lands back on `/store/uploads` with the new batch (`redirectOnCommit`). Nav item "Upload orders" (`/store/uploads`) prefix-highlights on `/new`.
- **Upload pipeline (`store/`):** own error catalog `store/errors.ts` (S-codes), reuses the shared `csv/parse.ts` engine, EXPLICIT header mapping from `store_order_fields.headers` (case-insensitive after trim — never auto-detected; a required field with no matching header fails fast). Two server actions (no session table): validate → error report OR "N new · M updated" → confirm → `commitStoreUpload` re-validates + writes transactionally (`writeStoreBatch`). **Upsert is a toggle** like the ads upload (default strict insert; on = update existing in place, keeping the row's original `upload_batch_id` so rollback removes only inserts). Rollback ≤24h (`upload.rollback`). Permissions: `store.upload` (+ `upload.upsert` for the toggle). Audit `store.upload_commit`/`store.upload_rollback`/`store.fields_update`.
- **Orders page (`/store/orders`, open to any brand member):** SERVER-paginated (100/page + total count — order volume reaches 100k+), URL-backed date range + order-id search ONLY (no other filters, deliberate), a totals footer (count + `SUM(total_amount)` over the whole filtered set), every defined field selectable in the Columns menu (custom columns rendered by type; hidden-key set in localStorage so new fields default visible), CSV export of the filtered set (≤10k). SAR via `sar()` in `lib/format.ts` (module-local; no USD conversion here — ad-spend blending is a later phase).
- **Order cleanup (`/store/uploads`, `store.cleanup`):** the Store twin of the ads record-cleanup tool — a danger-tinted card below the upload history. Filters (≥1 required, AND-combined): order-date range, upload batch, order-id(s) (exact / comma-separated). Preview (`previewStoreCleanup`: order count + SAR total + date span) → type-DELETE-to-confirm → transactional account-scoped hard delete (`deleteStoreOrders`). Audit `store.bulk_delete` with the filter set + the count actually removed. Sanctioned `store_orders` delete paths are now **batch rollback + this cleanup tool**.
- **Reconciliation (`/store/reconciliation`, read-open to any signed-in user):** compares store ORDER COUNTS vs platform-claimed CONVERSIONS per day — **counts only, NO revenue comparison anywhere** (a standing product decision; store revenue SAR / spend USD are optional hidden context columns, never diffed). No chart. A KPI summary row (MetricCards: Store orders · Platform conv. · Δ · Match rate = claimed/store, "—" when store=0) sits above the table — headline totals are mode-independent (both modes reconcile to them); in By-platform mode each tile additionally shows per-platform breakdown bars (platforms with data only, + the Unattributed bucket on the orders/Δ tiles so bar sums match the headline). Table with two modes: **Overview** (DataTable: Day, Store orders, Platform conv., Δ = store−claimed, Δ% = Δ/store — "—" when store=0, warn-tinted by |magnitude| since over- and under-claim are both discrepancies; weighted totals footer) and **By platform** (grouped-header table, the summary-table exception: per-platform [Store orders | Claimed | Δ] + an **Unattributed** group). Date range is the only filter (URL-backed); rows = days where either side has data, desc; ads side respects `excluded_from_aggregates=false`. **Attribution:** each order's source comes from a configured custom field (`accounts.store_source_field_key`); its raw value maps to a platform (or "not an ad platform") via `store_source_mappings` (explicit only — unmapped/empty/not-ad → Unattributed, so per-platform + unattributed always reconcile to the Overview count). Config lives in the **Order fields** tab on `/store/uploads` (`config.store`, audit `store.source_mapping_update`). By-platform shows a not-configured empty state until the source field is set; an unmapped-values banner links to config; days within 7 days of a platform's data horizon get a muted "still attributing" marker (visual only). Migration **0031** (additive: `accounts.store_source_field_key` + `store_source_mappings`).

## 5d. Budget module (v2 — its own sidebar section, 3 pages)

- **What:** a top-level **Budget** section (between Ads and Store in `nav-items.ts`) of THREE pages sharing `?month=YYYY-MM` (the section's nav links carry the current month, so switching pages never loses it; the shared month bar has ‹ › steppers + a year dropdown): **Overview** `/budget` (read-only verdict), **Plan** `/budget/plan` (the editor), **Pacing** `/budget/pacing` (plan vs actual over any date range). The former **Daily** and **History** pages merged into Pacing (2026-09) and are PERMANENT redirects to it — `/budget/daily` carries its query params across, `/budget/history` asks for the last twelve months grouped by month, which is what it used to show. Spend planned in **USD** per platform → budget objective (pickers derive from `lib/palette` / `BUDGET_OBJECTIVES`); revenue planned as ONE monthly **SAR** total per brand (no breakdown — deliberate). Any month editable (`budget.manage`, editor preset; audited `budget.update` with a diff summary incl. weight-override count + reserve) — no locking.
- **Day-weight plan curve (replaces v1's linear pacing EVERYWHERE in Budget):** each day of the month has a weight (default 1; only non-1 overrides are stored in `budget_day_weights`; valid 0 < w ≤ 10, UI steps 0.5). Plan-to-date = plan × Σweights(1..day) ÷ Σweights(all) (`curveFraction` in `lib/budget.ts`); a month with no overrides is EXACTLY v1's linear pacing (unit-pinned). ONE curve drives BOTH spend and revenue pacing, and the month-end projection = actual-to-date ÷ elapsed curve fraction (null → "—" when the fraction is 0). Edited on Plan via a weekday-aligned calendar grid (click day → 0.5-step stepper; weight→1 deletes the row; "Reset all to 1"; an override-count line above it — the old cumulative-curve SVG preview was removed).
- **Reserve budget:** `budget_targets.reserve_spend_usd` — contingency USD on top of the plan, deliberately **OUTSIDE the curve** (never in pacing/plan-to-date). Overview's reserve line reads "Plan $X + $Y reserve · Reserve used: $Z of $Y" where reserve-used = the month's UNPLANNED actual spend (combos with no plan row); warn when used > reserve. The spend projection is judged against plan+reserve ("within reserve" vs "over even with reserve"). Copy-from-last-month copies allocations + target + reserve + weights (day 31 dropped for shorter months via `mapWeightsToMonth`).
- **Overview:** 4 KPI tiles (spend / revenue / ROAS-via-rate / orders) with curve-based pacing verdict + month-end projections (current month only, warn-tinted by magnitude), the reserve line, the revenue block, per-platform summary cards (planned vs actual + pacing dot) deep-linking to `/budget/plan?month=…#platform-<key>` (DataTable `rowId` anchors), and the shared data-horizon note.
- **Budget objective buckets — a STANDING DECISION (2026-09).** Budget plans against its OWN objective axis, `BUDGET_OBJECTIVES` in `lib/budget.ts`: exactly **Awareness · Activation · Retargeting · Other**. `toBudgetObjective(campaignObjective)` maps the three mains one-to-one and everything else — Sales, Prospecting, Special Case, and anything a future campaign rename introduces — into **Other**; nothing outside Budget changes. The bucket is applied at every budget layer: `planSchema` (so the Plan editor can only store buckets), the Plan editor's pickers, actual-spend grouping (`getBudgetMonth().actualSpendByCombo` and `budgetPacingSeries`, folded in the query layer so no consumer can forget), and revision restore. **Restore folds legacy snapshots** through `mergeAllocationsToBuckets`, SUMMING rows that collapse onto the same (platform, bucket) — an old snapshot with Sales and Prospecting rows restores as one Other row rather than failing validation or colliding on the unique index. Migration **0041** (hand-written) did the same fold to the stored rows. Consequence, and the reason for the change: a future campaign-objective rename now touches `toBudgetObjective` only — it can never strand a `budget_allocations` row again. (Sales is currently mislabeled data; the team will reclassify those campaigns into the mains on the campaigns side.)
- **Allocation check — on OVERVIEW (2026-09).** Below the month's verdict: a read-only table grouped by the four buckets, each with its platforms beneath — `Planned · Actual · Pacing · Variance · Variance %` (Pacing only for the current month). A bucket×platform with actual spend but no allocation renders as a dimmed **unplanned** row, and the Actual total must equal the month's RAW `performance_records` total EXACTLY — the harness-pinned invariant, so money can never fall outside the table.
- **Pacing (`/budget/pacing`) — plan vs actual over any DATE RANGE.** URL-backed `from`/`to`/`groupBy`/`platforms`, so a view is shareable; the range defaults to the current month, or to the `?month=` the Budget nav links carry, and `granularity=monthly` (the retired History link) lands on the last twelve months grouped by month.
  - **Group by** Day · Week · Month buckets BOTH sides. Weeks are **Sunday-start calendar weeks CLIPPED to the range** (`weekBucketsInRange`) — partial first/last buckets rather than borrowing days the range didn't ask for. Month grouping replaces both the old "monthly granularity" and the old History page.
  - **Platforms** is a multi-select that scopes the actual spend AND the plan (a platform's plan = its allocations), so the comparison stays honest. Because store revenue has no per-platform attribution, an active platform filter LOCKS the metric to Spend with a one-line note — said, not hidden.
  - **Metric** Spend · Revenue · **ROAS**. Revenue and ROAS are all-platforms only — under a platform filter they render visibly LOCKED (disabled with a title) rather than silently switching. ROAS actual = bucket revenue ÷ (bucket spend × rate); the plan line is the **Target ROAS** = target-to-date ÷ (plan-to-date × rate); the Pacing column is actual − target ROAS, warn-tinted by magnitude like every other pacing verdict (and dashed when there is no target ROAS to measure against).
  - **Objectives** is a toggle (there is no "by platform" dimension — the filter does that job). Off = totals; on = one line per bucket in the series colors, and the table grows one BLOCK per bucket (`Actual · Plan-to-date · Pacing`) plus the total block, because the per-objective pacing is the point. It combines with the platform filter, spend only.
  - **Plan across an arbitrary range:** a day's planned spend = its month's scoped plan × (`curveFraction(d)` − `curveFraction(d−1)`), stitched across every month the range touches (`monthDayIncrements` / `stitchPlanByDay`, unit-tested to sum back to the month's plan and to make a cross-month range equal the sum of its parts). `budgetPlansForMonths(months)` fetches those months in **three queries — one per table with an `inArray`**, never a round-trip per month (`lib/db.ts` is `max: 1`). `budgetPacingSeries(from, to)` stays exactly two scans.
  - **Horizon semantics per bucket:** each side is known through its OWN horizon (`dataHorizon()` for spend, `storeDataHorizon()` for revenue). A bucket entirely past it is UNKNOWN — em-dashes, and the chart line ends rather than dropping to zero; one that straddles it sums only its known days and is marked "through Sep 4". The plan side always covers the bucket's real end (a plan is known in advance). `HorizonNote` stays at the foot.
- **Standing decision — objective renames:** campaign-objective renames now touch `toBudgetObjective` ONLY. `budget_allocations.objective` stores budget buckets, not campaign objectives, so it no longer needs sweeping (migration 0034's rule applied to the pre-0041 world).
- **Actuals — STANDING DECISIONS (do not "fix"):** actual spend = the month's `performance_records` **with NO exclusion filtering** (raw totals; budget answers "what did we actually spend", so its totals may differ slightly from dashboard aggregates, which do filter) — this applies to the per-day series too. Actual revenue = `SUM(store_orders.total_amount)` per month/day (store FACTS; claimed-vs-real analysis stays on Reconciliation) + order count as context.
- **Unplanned bucket invariant:** any (platform, objective) with actual spend but no plan row renders as a dimmed "unplanned" row inside its platform group — the spend table's actual total must equal the month's raw `performance_records` total exactly (harness-tested).
- **Currency:** revenue always SAR. Spend is USD natively with a USD↔SAR display toggle (per-user, localStorage `cw-budget-currency`, shared by all three pages) converting via the per-brand `accounts.usd_to_sar_rate` (default **3.77**, inline-editable on Plan with `budget.manage`, validated 0 < r ≤ 100). Target/actual **ROAS is always computed through the rate** (revenue SAR ÷ spend×rate), regardless of the toggle.
- **Pacing verdicts (Overview, current month only):** curve-based expected-to-date; deviations are warn-tinted by |magnitude| (over- and under-pace are both deviations — Reconciliation's Δ philosophy; never green/red). Past months show plain plan-vs-actual. Pure math in `lib/budget.ts` (unit-tested).
- **Rate is applied RETROACTIVELY (confirmed behavior).** Every SAR conversion and every ROAS in the module — including Pacing's past months — uses the brand's CURRENT `accounts.usd_to_sar_rate`, not the rate that was in force during that month. Editing the rate therefore restates history. That is the intended behaviour today (one rate per brand, no snapshot); a per-month rate snapshot is a possible future change, and would need a schema column plus a backfill.
- Edit mode = house draft + dirty-check + explicit Save (full-replace per month, weights + reserve included) with an optional one-line note; CSV export in the displayed currency. Migrations **0035** (v1: the two tables + the rate column) + **0036** (v2, additive: `budget_day_weights` + `budget_targets.reserve_spend_usd`) + **0040** (additive: `budget_plan_revisions`).
- **Plan is a PURE PLANNING surface (2026-09 decision).** `/budget/plan` shows intent only — Platform/objective · Planned · % share in view mode — and carries NO actuals: the Actual, Pacing, Variance and Variance % columns and the "unplanned" ghost rows were removed. Plan-vs-actual lives on Overview and Pacing. `getBudgetMonth()` still returns `actualSpendByCombo` for its other callers; the Plan page simply ignores it.
- **Editing is a TOP-DOWN cascade (2026-09).** Edit mode is entered in one order: **1. Targets** — total spend budget (USD, the primary input), revenue target (SAR, one monthly total by decision), and the reserve as a DUAL ENTRY (an amount OR a % of the total; the % field is raw-text-buffered like the share inputs so a keystroke is never reformatted under the caret, and it is disabled until a total exists). Units sit inside their inputs' boxes, and "Allocatable · Reserve" is its own line under the fields. **2 + 3. Platform and objective shares** — a grid of ALWAYS-OPEN platform cards (2×2 from `sm`, one column below; no expand/collapse): each card's header is the platform's % of the ALLOCATABLE with its derived USD, and its body is the four buckets, each a % of THAT platform's amount with its derived USD, a per-platform sum, and "Distribute remaining evenly" / "Normalize to 100%". An unplanned platform still shows its four rows, disabled; a planned one with no money yet can take its split but its dollar fields are disabled (there is no parent to be a share of). Enter-advance walks the cards in DOM = visual order, card by card. **4. Day curve** — the existing month-general calendar; its small cumulative SVG preview was deleted, the override-count line and grid stay.
  - **Percentages are the PRIMARY input; amounts stay editable as secondary** — typing a dollar figure back-computes its share against the parent, which is held fixed. It all runs through cents-exact pure helpers in `lib/budget.ts` (`allocatableFromTotal`, `reserveShare`/`reserveFromShare`, `amountsFromShares`, `shareFromAmount`, `sharesComplete`, `distributeShareEvenly`, `normalizeShares`, `moveMoney`), unit-tested.
  - **Storage and round-trip unchanged:** SAVE stores the derived amounts in today's `planSchema` shape; EDIT reconstructs the shares from the stored amounts (total = Σ allocations + reserve) at full precision, so a round-trip returns the same amounts to the cent. Revisions, audit and copy flows are untouched.
- **Save is blocked below 100% — a user decision.** Platform shares must reach exactly 100% of the allocatable, and every platform with a share must have objective shares reaching exactly 100%. The blocked banner names each gap precisely ("Snapchat objectives: 85.0% — 15.0% unassigned"), and "Distribute remaining evenly" is the one-click fix. Money deliberately not committed belongs in the RESERVE, nowhere else. Rounding never blocks — the check tolerates float dust only (`SHARE_EPSILON`) and the derived amounts are cents-exact by construction, so 33.3/33.3/33.4 is complete.
- **Two mid-month operations, deliberately distinct.** **Change the total** (or the reserve) RESCALES every derived amount through the current shares — a platform on 50% stays on 50% — with an inline note saying so while the total field has focus. **Move money** is a separate dialog: pick an amount, a source (the reserve, another platform, or **new money**, which grows the total) and a target platform. The target's dollars rise by exactly the amount and the source's fall by exactly it; every other platform keeps its exact dollars while only its displayed share moves, and inside the target the objective shares hold so the money spreads proportionally. The pure helper is `moveMoney` in `lib/budget.ts` — it works in the AMOUNTS domain against the caller's allocatable (`total − reserve`), never Σ amounts, which is smaller while a split is incomplete. The revision note pre-fills with both ends ("Moved $2,000 TikTok → Snapchat").
- **Seeding a plan: amounts vs shares.** "Same split, new total" is the common real task, so the Copy dialog offers two modes — **Copy amounts** (today's server-side `copyBudgetFromMonth`, replacing the month's plan dollar for dollar) and **Start from its shares**, which writes NOTHING: it opens the editor with the source month's platform/objective shares and day weights reconstructed, total blank and focused. A shortcut button beside Edit plan (and in the empty state) does the same from the most recent earlier planned month, whose plan the Plan page fetches conditionally via `budgetPlansForMonths([seedMonth])`. Both Plan and Overview turn a no-plan month into a rollover nudge rather than a dead end. `normalizeShares` (scale proportionally to exactly 100%) sits beside "distribute remaining evenly" (pad the gap equally) at both levels — different intents, both kept.
- **The plan-curve editor is a calendar BESIDE a live bar chart.** The model is normalized shares — weighting a day gives it a bigger slice and shrinks the others, so the month always totals the budget — and the bars are how that becomes visible: one bar per day, height = that day's planned dollars (`monthDayIncrements`, the same numbers the pacing math uses, unit-pinned to agree), tinted for weighted days, clickable and selection-synced with the calendar. With no total set yet the bars are labelled as a share of plan instead. Below: the 0.5-step stepper, a typed weight snapped to the 0.5 grid, and preset chips — Paydays (10th & 25th) ×3, Weekends (Fri–Sat, the Saudi weekend) ×0.5, Clear all — all draft-only.
- **Copy from ANY month.** `copyBudgetFromMonth({ month, from })` (replacing `copyBudgetFromLastMonth`) copies allocations + target + reserve + weights from any month that has a plan, chosen in a dialog (button label: **Copy**) fed by `plannedMonths()` (distinct months with an allocation OR a target row, newest first; default = the previous month when it has one). Replace-entirely semantics and the copied-count toast are unchanged.
- **Plan revisions (`budget_plan_revisions`, migration 0040).** Any month is still editable with no locking — revisions are the guard alongside the audit trail. Every write that changes a plan (save, copy, restore) appends a snapshot of the plan **as it stands afterwards** — `{allocations, plannedRevenueSar, reserveSpendUsd, dayWeights}` as jsonb — **inside the same transaction** as the write, with the author and an optional note ("What changed?", ≤200 chars; copy and restore write their own notes). `listPlanRevisions(month)` reads a month's revisions newest-first, bounded at 50, joined to `users` for the author label and summarized from the snapshot. `restorePlanRevision({revisionId})` (`budget.manage`) loads the revision **account-scoped**, re-validates the snapshot through `planSchema` — so one predating a vocabulary change (a retired objective, say) fails loudly instead of half-applying — then replaces the month and records a revision of its own; audited `budget.update` with `op:"restore"`. The Plan tab's **Revisions** drawer lists them for every member (Restore is gated), shows the selected snapshot read-only, and diffs it against the current plan (added / removed / changed allocations with old → new, plus revenue target, reserve and weighted-day count). Months planned before this shipped simply have an empty list.

## 6. CSV ingestion (binding spec: `docs/validation-spec.md` v1.2)

Five stages — parse → header mapping → row validation → cross-row/file checks → DB-level duplicate checks. Stages 1–2 fail fast; 3–5 collect all errors into one report. **All-or-nothing:** nothing is written unless the whole file is clean and the user confirms; the commit is a single transaction (batch row + chunked inserts), backstopped by the unique index. Error codes live exclusively in `csv/errors.ts`. Matching is deliberately *forgiving on whitespace* (cells trimmed; no NFC normalization; blank numeric cells read as 0) — this is intended behavior as of v1.2, do not "fix" it to strict. **Upsert mode** (opt-in per upload) skips the already-imported rejection and updates existing rows in place (batched `UPDATE … FROM VALUES`); built for rolling attribution backfills; updates are not rollback-able. XLSX is accepted alongside CSV.

## 7. Aggregation rules (CRITICAL — never violate)

- Every blended metric = **weighted average via component sums**: `SUM(num) / NULLIF(SUM(den), 0)`. Never `AVG(ratio)`.
- All fragments imported from `lib/metrics.ts` (incl. `aov`, `roas`, video hook/hold on 2s + quartile columns). `NULLIF` ⇒ undefined renders as `—`, never 0 or ∞.
- Aggregations filter `excluded_from_aggregates = false` by default; the shared Excluded toggle (`?includeExcluded=1|0`) opts out per page and is now on EVERY aggregate surface (dashboard, funnel, trends ×5, summary, campaigns list + detail, Library, creative detail, Compare, Reconciliation's ads side). The toggle state is a saved per-user preference (`users.include_excluded`): explicit URL param → saved preference → hidden (`resolveIncludeExcluded`). Detail views always show excluded rows with a badge (rule-excluded rows say so in the badge tooltip). Status derivation and Compare's dimension pickers deliberately stay excluded-hidden.
- Raw SQL only in `db/queries/performance.ts`, wrapped in typed helpers.

### 7.1 Query-shape rules (2026-09 performance pass)

- **`lib/db.ts` holds ONE connection per instance** (`max: 1`, required for serverless). `Promise.all` therefore executes SERIALLY — batching queries is about not stalling on unrelated round-trips, never about parallelism. The lever that actually moves latency is the NUMBER of queries.
- **Status derives from ONE cached set of scans.** `brandStatusInputs()` in `db/queries/creative-status.ts` (React `cache()`, per request) fetches the three raw datasets — per-creative activity, per-platform freshness, overrides — once, unrestricted; `creativeStatusMap`, `creativeStatusBreakdown` and the status-flow builders derive from it in JS. Campaign status can't share the activity scan (it groups by campaign) but reads the same cached `platformSpendFreshness()`. **Never add another direct status scan** — derive from the cached inputs. The `asOf` point-in-time variant is the sanctioned exception: it reconstructs a PAST day and keeps its own date-bounded queries.
- **Don't restrict a shared scan with a big `IN (…)`.** Callers pass no ids and filter the returned map in JS; an id list of every visible row cost more than the scan it narrowed, and couldn't be shared between callers.
- **Indexes (migration 0039) match that read shape.** Two PARTIAL indexes on `performance_records` — `(account_id, platform, date DESC)` and `(account_id, creative_id, platform, date)`, both `WHERE spend > 0 AND excluded_from_aggregates = false` — cover the aggregate default and the status scans' predicate, so they index only the rows those queries can return. `pg_trgm` + a GIN index serves the Orders page's substring search on `store_orders.order_id`, which no b-tree can. The superseded `perf_date_idx` and `perf_excluded_idx` were dropped in the same migration. A plain `CREATE INDEX` briefly blocks writes; at current volume that is acceptable, and `CONCURRENTLY` is the escape hatch if the table grows.
